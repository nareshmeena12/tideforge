# G2 calendar engine, G3.2, G3.4: table, mechanism checks, audit, CPU throughput (2026-10-28)

Code: `tideforge/gen/ext/g2_*.py`, table builder `tools/build_calendars.py`, tests `tests/test_gen_g2.py` (run with `-s`
for the numbers), galleries `tools/gallery_cal.py` (holidays and weekends shaded) and `tools/gallery.py`. Measurements of
the generator, not results.

## Calendar table (calendars_v1.npz, committed)

- 67 calendars (55 countries + 12 subdivisions), 18,628 days 1990-01-01..2040-12-31, holidays 0.107,
  sha256 20de60db420e36da0c98712fa95cc7e508189bafff0863e43dd05c1ba19c4bd1, 52 kB. `--check` rebuilds and compares.
- 1,794 holiday names, 110 unmatched -> "other" (listed per calendar in calendars_v1_report.txt for review).
- Gaps in the package (never filled with invented dates; each calendar has a valid year range from its key festivals,
  and windows are placed inside it):

| calendar | valid years | why |
|---|---|---|
| IN, IN-MH | 2001-2035 | Diwali only in those years |
| LK | 2004-2026 | Diwali only in those years |
| NP | 2010-2035 | Tihar (Bhai Tika) / Diwali only in those years |
| TW | 1998-2040 | the package starts in 1998 |
| HK | 2022-2040 | Buddha's Birthday only from 2022 (probably a naming change in the package) |
| PH | 2024-2040 | Eid al-Fitr from 2002, Eid al-Adha from 2010, Lunar New Year from 2012 (law changes) |
| ID | 2003-2040 | Lunar New Year a holiday from 2003 (law change) |

  The rule treats a key festival present in >= 30% of the years as required, so law changes that added a festival (PH, ID)
  shorten the range too. Many Islamic dates after the present are marked "(estimated)" by the package.

## Mechanism checks (tests/test_gen_g2.py)

| check | measured |
|---|---|
| Islamic holidays recur 353-356 days later (SA / EG) | 0.98 / 0.93 of starts |
| SA first Islamic holiday of the year | median shift -11 days a year |
| Lunar New Year (CN / SG / VN) moves -10..-12 or +18..+20 days | 0.96 / 1.00 / 0.98 of years |
| Jewish holidays recur 353-356 or 382-386 days later (IL) | 0.98 |
| weekend rules (SA Thu-Fri -> Fri-Sat 2013, AE Fri-Sat -> Sat-Sun 2022, NP Sat) | exact |
| weekend effect below weekday effect (draw P = 0.80) | 0.80 of rows; flags = the calendar's own weekend days |
| holiday day effect = its type's draw (isolated holidays) | 1.00 (1,726 days) |
| run-up: day before has the same sign | 0.89 |
| rebound: day after non-zero | 0.77 |
| invented calendars equal to a real one (512 x 2015) | none |
| drifting invented holidays | every 354-355 days |
| DST rows: one skipped hour per spring change, one repeated per autumn change | exact (end-of-window clamp excluded) |
| weekly rows show the week of 25 Dec | all |
| P2 oracle: MAE with flags / without on holiday and day-before days (daily cal_cov rows) | median 0.834 (93 rows) |
| season_short: dominant cycles of the replaced seasonal part | median 2.50 |

DST: steps past the window's end after a spring-forward are clamped to the last step (at most one hour repeated at the end).

The audit's shape features barely see calendar effects. The covariate share moves 8.5-10.2% without any group change:
cal_engine changes values before the noise layer, so the later global draws (group kinds included) differ, and 512
blocks give about +-1 point. Short-season detector (added 2026-10-28): the dominant frequency of the detrended row is at
1.5-3 cycles and holds >= 25% of the power; random walks give B0 an 11.7% baseline, so G3.4 reads +2.7 points, not the
share of rows the switch touches.
